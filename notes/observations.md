## Сессия 2026-04-22 (до HSV-верификации, до перерегистрации)

Источник: скриншоты + записи пользователя.

### Производительность (proc time)

- 0 объектов: 150–200 ms
- 1 объект: 240–250 ms
- 2 объекта: 290–330 ms
- 4 объекта: 440–450 ms
- Рост линейный — каждый объект добавляет ~70–80 ms (FLANN knnMatch × N объектов)

### Условия съёмки

- Камера не строго вертикальна — держится на стопке книг + опоре, лёгкий наклон
- «Плоская» плоскость поля — под небольшим углом к объективу
- Использовалась брошь 1 см на краю фишки для наклона ~20–30° при регистрации; визуально кадр не менялся

### Стабильность детекции

- chip-50 (чёрная): bbox джиттерит даже в одиночку при смещении от точки регистрации
- chip-5 (красная): иногда не детектируется рядом с chip-50 на одной горизонтали; chip-50 "съедает" chip-5
- chip-25 (синяя): больше ложных срабатываний с chip-5 (два box'а на каждой)
- chip-10: зарегистрирована на другом месте, детектируется хорошо
- Все 4 фишки: ~90–100 признаков после регистрации (per_shot=100); зелёные боксы редко строго прямоугольные

## Сессия 2026-04-24 (перерегистрация, per_shot=150, 8 объектов)

Источник: scanner.log + скриншоты.

### Условия съёмки

- Первые 4 фишки (chip-5, chip-25, chip-50, chip-1) — в нормальном освещении
- chip-10 и все последующие — в тени (телефон/плотный объект убирает блики от камеры)
- Тень улучшает качество захвата для блестящих объектов: меньше бликов → стабильнее ключевые точки

### Количество признаков (per_shot=150, 5 снимков)

| Объект    | Признаков | Примечание                       |
| --------- | --------- | -------------------------------- |
| chip-10   | 750       | максимум (150×5)                 |
| chip-25   | 696       |                                  |
| chip-5    | 680       |                                  |
| chip-1    | 622       | белая фишка                      |
| chip-50   | 601       | чёрная с глянцем                 |
| vili      | 335       | объёмная металлическая подставка |
| lil-blue  | 266       | синий камень, мало текстуры      |
| lil-white | 224       | USB-модуль, мало текстуры        |

Закономерность: больше выраженной текстуры → больше признаков → лучше детекция.

### Производительность

- 8 зарегистрированных, 5 активных: ~574 ms proc time, ~1.7 fps
- Рост с ~70–80 ms/объект подтверждается

### Детекция по объектам

**chip-5 (красная):** Стабильна. Редкие кратковременные пропадания (≤10 с), затем восстанавливается.

**chip-25 (синяя):** Заметно хуже чем в сессии 2. Частые пропадания при 8 зарегистрированных. С меньшим числом объектов — хорошо.

**chip-50 (чёрная, глянец):** Много циклов ПОЯВИЛАСЬ/ПРОПАЛА в логе (~каждые 1–3 мин). Bbox нормальный когда виден. При регистрации снимок 4 занял 43 с — возможно, неудачное освещение.

**chip-1 (белая):** Редкие детекции. Bbox деформирован — почти прямая линия. Причины: 1) HSV-фильтр отклоняет (белый близок к белому фону/бликам), 2) низкий контраст на белом фоне.

**chip-10 (зелёная):** Редкие детекции. Bbox деформирован — почти прямая линия. Причина неясна: признаков максимум (750), цвет хорошо отличим. Возможно, регистрация в тени дала другой профиль, чем условия детекции (нормальное освещение).

**lil-blue (синий камень):** 266 признаков — ниже порога надёжной детекции. Нестабильна, частые пропадания. Под прямым углом иногда работает.

**vili (металлическая подставка):** 335 признаков. Нестабильна. Иногда проскакивает.

**lil-white (USB-модуль):** 224 признака. Почти не детектируется. Первая регистрация прервана (ESC, 33 признака, опечатка в имени), переделана полностью — всё равно 224.

### "Восьмёрка" и деформированный bbox

- chip-10, chip-50: периодическая "восьмёрка"
- chip-1: bbox в виде почти прямой линии — более крайняя деградация гомографии

## Сессия 2026-04-29 (однородный HSV-фон, 3×4 поле, 5 объектов, текстовые обводки)

Источник: живое тестирование с новой конфигурацией фона.

### Условия съёмки

- Однородный по HSV цвет фона поля (новая конфигурация)
- Поле: 3 столбца × 4 строки (12 клеток)
- Объекты: chip-5 (красная), chip-25 (синяя), chip-50 (чёрная), chip-1 (белая), lil-blue / lil-white (слабо текстурированные)

### Результаты регистрации

- **Успешно:** chip-5, chip-25, chip-50, chip-1 — все 5 зарегистрировались успешно в drag-режиме
- **Трудности:**
  - eks (cutout chip) — не удалось зарегистрировать (объект вне поля или вне фокуса во время съёмки)
  - lil-white (USB-модуль) — детектируется нестабильно, низкий контраст к фону, нужна регистрация в лучших условиях

### Калибровка поля и визуализация

- **Ввод углов:** Пользователь интуитивно вводил слева направо сверху вниз (не TL→TR→BR→BL)
  - Решение: обновлены подсказки на "Top-Left / Top-Right / Bottom-Right / Bottom-Left" (полные слова вместо сокращений) ✓
- **Сетка:** Хорошо видима, чистая зелёная линия
- **Позиции фишек в сетке:** Все 5 активных фишек корректно отображают:
  - Номер клетки (1-12, 1-indexed)
  - Координаты (row, col) в матричном виде
  - Пример: "chip-5 [cell 8 (3,2)]"

### Качество детекции в поле

- **Успешные объекты (chip-5, chip-25):** Стабильно детектируются, позиция обновляется каждый кадр
- **Проблемные объекты:**
  - eks: не регистрировалась → нет данных о детекции
  - lil-white: низкая текстура → редкие детекции даже при фокусе на ней
  - chip-50: иногда пропадает при множестве объектов (подтверждение наблюдения из сессии 2 и 3)

### UI и видимость текста

- **Обновление:** Все текстовые метки на кадре получили чёрную обводку (\_putText_stroked)
- **Результат:** Надписи хорошо читаются на переменном фоне (ранее была единственная претензия)
- Применено к: метки детекций, калибровка, очередь ходов, режим регистрации, подсказки, элементы управления

## Сессия 2026-04-30 (FSM ходов, тест игрового цикла)

Источник: живое тестирование после интеграции GameEngine + FSM.

### Детекция

- lil-blue успешно обрабатывалась системой при ходе, пусть медленнее, чем chip-10 — фокусированная детекция компенсирует слабую текстуру
- chip-10 получила cell 2 в памяти из-за мгновенного визуального артефакта → находясь на cell 1, не засчитывалась. Помогло disappear + повторный appear (сброс chip_cells)

### Игровой цикл

- MOVE_FORWARD, MOVE_BACK, FINISH — все успешно сработали
- EXTRA_TURN: правило сработало с пропуском на 2 клетки вперёд (поведение корректно)
- MOVE_BACK без модификации правила вызвал софтлок (фишка ушла за cell 1). Решено изменением правила — `max(1, ...)` в движке держит в пределах поля

### Баги (исправлены)

- Первый ход шёл второму игроку: `turns.start()` при `[S]` смещал индекс. Убрано — первый `[N]` стартует очередь с 0
- Инструкция на первый ход не показывалась: `_chip_cells` уже помнила клетку с предыдущей детекции → `on_chip_at_cell` не вызывался. Исправлено: при `begin_turn` сбрасываем запись активной фишки

### Открытый баг

- Визуальный артефакт (1 кадр ошибочной клетки) может сдвинуть `_chip_cells` → фишка на правильной клетке не регистрируется. Временное решение: убрать фишку и положить обратно (сброс). Нужен дебаунс (N кадров на одной клетке перед фиксацией)

## Общие наблюдения

- Объекты с ≤300 признаками (lil-blue, vili, lil-white) детектируются плохо или почти никак
- Белые объекты (chip-1): HSV-верификация может отклонять из-за близости к фону
- Чёрные объекты (chip-50): низкий V → нестабильная HSV-верификация, глянец добавляет нестабильность ключевых точек
- Регистрация в тени помогает для глянцевых объектов
- chip-5 и chip-25 — эталон стабильной детекции при текущей системе
- **Однородный HSV-фон улучшает общую стабильность** по сравнению с пестрым фоном из сессии 2–3

## Сессия 2026-05-04 (дебаунс, дайс-ролл, HTTP, удаление игрока)

Источник: живое тестирование после интеграции дебаунса, дайс-ролла, HTTP сервера и синхронизации удаления игроков.

### Дебаунс

- ✓ Дебаунс (3 frame requirement) сработал — visual glitch не поймана
- ✓ Игра прошла успешно без софтлоков

### Дайс-ролл

- ✓ Дайс-ролл вычисляется корректно (1–6 случайно)
- ✓ expected_cell рассчитывается как current_cell + dice_roll
- ⚠️ На первом ходе фишки "выскакивают" на expected_cell вместо стояния на cell 1 перед движением
  - Технически верно (старт на cell 0, движение на первый ход)
  - UX рекомендация: показать начальную позицию перед движением

### Удаление игрока (баг)

- **Проблема:** При удалении игрока во время его хода, следующий игрок не получает dice_roll
  - Последовательность: m3 финишировал → показано "Press [N]" → удалён m2 → [N] → m1 не получил roll
- **Корневая причина:** TurnManager удаляет из очереди, но GameEngine.state не синхронизируется
- **Решение:** TurnManager.remove() теперь возвращает chip_id, GameScanner удаляет из engine.state
- **Статус:** Фиксировано в текущем коммите

### HTTP события

- ✓ HTTP сервер стартует и отправляет события
- ✓ Events endpoint показывает последние события с полной информацией
- ✓ State endpoint показывает текущее состояние игры
